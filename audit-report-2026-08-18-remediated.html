Remediation outcomes

Privacy and tenant data

  • Provenance is explicit, private, non-publishing, and commitment-only by default.
  • Public reveal/publication requires authenticated request-level consent.
  • Receipts use UUIDs, tenant/project ownership, TTL/capacity, and disclosure guards.
  • An async public store/factory boundary supports a durable implementation; unsafe memory use is explicit and fail-closed.

Fetch and billing

  • All Spider routes share status rejection, redirect refusal, one deadline, and streamed byte caps.
  • Adaptive fallback affects the current request only for bounded challenge cases.
  • Execution order is preflight → validated pending result → request-bound enforced capture → evidence finalization.
  • Subject, tenant, project, route, exact plan, pricing, and caller key bind idempotency; unsafe replays fail closed.

MCP and authentication

  • Host and Origin allow-lists are enabled; attacker headers are tested.
  • Issuer, audience, scope, and subject are exact; OAuth context is validated once and reused.
  • Stateless RMCP, cancellation tokens, deadlines, and bounded draining stop detached work.
  • Tool descriptors truthfully disclose credit, receipt, and provenance side effects.

Egress and lifecycle

  • Local checks block metadata, loopback, private, link-local, reserved, mixed DNS, and mapped/translated IPv6 bypasses.
  • Source operations require an authenticated same-origin egress capability and live readiness probe.
  • Liveness and readiness are distinct; graceful shutdown and timeout cancellation have runtime regressions.
  • Low-cardinality process-safe metrics are exposed and concurrency-tested.

Build and supply chain

  • The repository is self-contained and uses an exact Rust 1.94.0 toolchain.
  • Lockfile advisories are clean; CI pins workflow actions and audit tooling.
  • Dependabot, cargo-deny, Gitleaks, fresh-checkout, and hardened container gates are blocking.
  • The container is multi-stage, non-root, digest-pinned, and runtime-smoked.

Contracts and maintainability

  • Strict unknown-field schemas cover HTTP, MCP, and nested provenance inputs.
  • OpenAPI enumerates audited response behavior; the MCP example and operations runbook match runtime behavior.
  • Experimental/demo artifacts, stale package identity, inert features, and misspelled route aliases are removed.
  • Security, contributing, dependency policy, release blockers, and changelog documents are checked in.

Release blockers

  1. License. The repository owner must select an authoritative license and add matching Cargo metadata before public redistribution.
  2. Durable receipts. Production must supply a shared, tenant-scoped, expiring receipt adapter. The included memory implementation is intentionally non-durable and single-replica.
  3. Atomic credits and replay. The Livy backend must add reserve/capture/cancel bound to the caller key and request fingerprint, including authoritative replay of the original resolver result.
  4. Remote egress. The Spider/policy deployment must enforce public-only DNS answers and every redirect hop at the machine making the request, and expose the authenticated readiness capability.

Final recommendation

Merge or deploy the remediated code only into an environment that remains fail-closed while the four blockers are open. Close each blocker with an integration test and operations-runbook update, then run the same CI and an environment-level penetration/egress test before changing the production-readiness decision.

Scope: this repository contains no on-chain Solana program, so signer/PDA/account-ownership and compute-unit checks were not applicable. This was a code, dependency, contract, local boundary, and fork-CI audit—not a formal penetration test of deployed Livy, Spider, DNS, proxy, or storage infrastructure.
