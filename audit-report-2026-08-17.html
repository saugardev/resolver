Executive decision

The service has a solid module layout, bounded request bodies, route-level OAuth scopes, sanitized public errors, safe URL logging, and 39 passing unit tests. Those strengths are outweighed by two release-blocking security defects and several boundary failures.

  • Provenance may turn on implicitly and defaults toward irreversible public publication of URLs and response data.
  • Receipt reads have no tenant/project ownership check; IDs are predictable and storage is unbounded and process-local.
  • A reproduced Spider HTTP 500 is billed and returned as HTTP 200 with a new receipt.
  • The current checkout cannot build from a clean clone because a required sibling path dependency is missing.

Detailed findings

Critical C-01

Optional provenance can activate implicitly and publish sensitive resolver data by default

Impact. Merely setting the backend URL used by credits can enable provenance. With the remaining defaults, visibility is public, managed publication is on, the full source URL is a public schema field, and upstream JSON up to 256 KiB can be sent to irreversible publication. Query-string secrets, authenticated-page content, returned headers, and returned cookies are therefore at risk.

Evidence. src/provenance.rs:164-188, 589, 673-723, 936-943. Reproduction with only LIVY_BACKEND_BASE_URL set caused startup to panic for missing ITA_API_KEY, proving the implicit activation path. With valid attestation credentials it proceeds toward publication.

Fix. Require explicit opt-in and make every publication choice fail-closed. Hash or redact source query strings and require per-request consent before revealing an artifact.

let enabled = env_bool("LIVY_PROVENANCE_ENABLED")?.unwrap_or(false);
let visibility = env_or("LIVY_PROVENANCE_VISIBILITY", "private");
let managed_publication = env_bool("LIVY_PROVENANCE_MANAGED_PUBLICATION")?
    .unwrap_or(false);
let publish_response_artifact = env_bool(
    "LIVY_PROVENANCE_PUBLISH_RESPONSE_ARTIFACT"
)?.unwrap_or(false);

// Public schema field should be a redacted URL or commitment, not the raw URL.
schema_field(4, "source_sha256", Json, json!(sha256(source)), true);
Critical C-02

Receipt storage is cross-tenant, predictable, unbounded, volatile, and not replica-safe

Impact. Any token with resolver:receipt:read can read any receipt if it knows or guesses the ID. IDs are timestamp-plus-counter values, records include the source URL, and lookup checks only the ID. The map has no TTL or capacity, disappears on restart, and produces random 404s behind multiple replicas.

Evidence. src/api.rs:217-228; src/fetch.rs:28-29, 663-725.

Fix. Store ownership at creation and query by the authenticated tenant/project. Use a durable bounded store, cryptographically strong identifiers, expiry, and explicit deletion.

struct ReceiptRecord {
    id: Uuid,
    tenant_id: String,
    project_id: String,
    expires_at: DateTime<Utc>,
    receipt: Receipt,
}

store.get_receipt(
    auth.tenant_id.as_deref().ok_or(Unauthorized)?,
    auth.project_id.as_deref().ok_or(Unauthorized)?,
    id,
).await?
High H-01

Spider non-success HTTP responses are accepted as successful, billable resolver results

Impact. The upstream client preserves most non-2xx responses as normal JSON values. The resolver only checks status/error on the first array item. Object-shaped errors therefore create receipts and provenance and return HTTP 200 after the credit debit.

Evidence. src/fetch.rs:73-107, 642-660. A local mock returning Spider HTTP 500 reproduced resolver HTTP 200 with a new receipt.

Fix. Patch or upgrade spider-client so every non-success response goes through error_for_status(). Keep a defensive payload check and test that failures produce 502, no receipt, and no provenance. Decide and document whether failed attempts are charged or refunded.

let response = client.send().await?;
let response = response.error_for_status()?;
let data = parse_response(response).await?;

#[tokio::test]
async fn spider_500_maps_to_502_without_receipt_or_provenance() { /* mock server */ }
High H-02

MCP DNS-rebinding protection is explicitly disabled

Impact. RMCP's allowed-host check exists to protect local servers from DNS rebinding and warns against disabling it for public deployments. This service clears the list. Risk is highest in the documented local mode where OAuth is disabled.

Evidence. src/main.rs:130-132.

Fix. Configure explicit local and production hostnames; do not use an empty allow-list. Add tests for accepted and attacker-controlled Host values.

StreamableHttpServerConfig::default().with_allowed_hosts([
    "localhost",
    "127.0.0.1",
    "resolver.api.livylabs.xyz",
])
High H-03

Private, loopback, link-local, and cloud-metadata destinations are allowed without an enforced egress policy

Impact. The resolver is an authenticated SSRF primitive by design. The repository contains no gateway or network policy to enforce the README's requirement to block metadata and other sensitive destinations. Redirects and DNS rebinding at the fetched destination also need enforcement.

Evidence. src/types.rs:352-377 and the explicit private-address unit test; README.md:174-178.

Fix. Split public-source and internal-source capabilities. Default-deny loopback, private, link-local, multicast, and metadata IP ranges after every DNS resolution and redirect. Put internal resolution behind a separate scope and deployment with an explicit allow-list and egress firewall.

enum SourcePolicy { PublicInternet, InternalAllowlist }

validate_resolved_ips(&url, SourcePolicy::PublicInternet)?;
// Reject 127/8, ::1, RFC1918, 169.254/16, fc00::/7, metadata hostnames, etc.
// Re-run the check for each redirect target.
High H-04

Availability bounds stop at request bodies; responses, provenance calls, and MCP sessions remain unbounded

Impact. Spider JSON/text is fully buffered without a maximum, then cloned for fallback/provenance and serialized again. The provenance HTTP client has no timeout on MCP calls. RMCP's default local session manager has no repository-configured session cap or idle expiry. These paths permit memory growth and hung requests even though product request bodies and product duration are bounded.

Evidence. src/provenance.rs:238; src/mcp.rs:278-283, 307-320; src/main.rs:55. Receipt growth is also covered by C-02.

Fix. Stream and cap upstream bodies before JSON parsing, avoid whole-response clones, set connect/request timeouts on every client, and use a session manager with maximum sessions plus idle eviction (or stateless MCP if compatible).

const MAX_UPSTREAM_BYTES: usize = 8 * 1024 * 1024;
let http = reqwest::Client::builder()
    .connect_timeout(Duration::from_secs(5))
    .timeout(Duration::from_secs(20))
    .build()?;

let bytes = read_stream_bounded(response.bytes_stream(), MAX_UPSTREAM_BYTES).await?;
High H-05

The repository is not reproducibly buildable and has no CI safety net

Impact. A clean clone cannot check, test, lint, or build because Cargo.toml points outside the repository. No workflow clones the companion project or runs quality/security gates.

Evidence. Cargo.toml:16. All three commands fail in this checkout with missing ../livy-core/packages/provenance-sdk/Cargo.toml. There is no .github/workflows directory.

livy-provenance-sdk = {

High H-06

Tests cover helpers, not security and billing boundaries

Impact. All 39 tests pass while the false-success, cross-tenant receipt, implicit provenance, disabled-host, double-introspection, and billing-idempotency defects remain. There are no integration, end-to-end, concurrency, or property tests.

Evidence. Tests live only inside src/*.rs; no tests/ directory exists.

Medium M-01

Compatibility and snapshot routes lose OAuth-scoped provenance context

Impact. /fetchfast and /fetchunblock debit the authenticated tenant, then call fetch methods with no auth context. Provenance falls back to a legacy service key, fails in production, or is recorded outside the user's tenant/project. /snapshot neither stores a resolver receipt nor records provenance despite its name and the broad README claim.

Evidence. src/api.rs:198-266; src/fetch.rs:145-150, 201-219, 222-238.

Fix. Route every endpoint through one authenticated execution pipeline; pass Some(&auth_context) to provenance and store the same tenant-owned receipt shape. Deprecate duplicate compatibility paths after migration.

fetcher
  .get_fast_data_with_receipt_with_auth(&payload.source, Some(&auth_context))
  .await?;

// Implement snapshot through product_fetch_with_auth rather than a parallel path.
Medium M-02

Product billing has no retry idempotency and does not enforce the debit outcome

Impact. MCP accepts an idempotency key, but every product retry creates a new nonce-based key and can charge again. Successful debit responses proceed even when enforced is false. Receipt reads, crawl, screenshots, and simple fetches all use the same configurable amount, and failed-upstream billing policy is undocumented.

Evidence. src/credits.rs:71-92, 185-217; src/api.rs:270-315.

Fix. Accept and validate Idempotency-Key on product mutations, scope it to tenant/project/route, distinguish replay from skipped enforcement, define route pricing, and document/refund failed-upstream behavior.

let key = ProductIdempotencyKey {
    tenant_id, project_id, route, caller_key: header_value,
};
let outcome = credits.debit_product_request(..., Some(key)).await?;
ensure!(outcome.enforced || outcome.mode == "idempotent_replay", CreditsDisabled);
Medium M-03

“Adaptive fallback” does not rescue the current request

Impact. Challenge-page detection is spawned after a successful fast result, so the user receives the challenge page; only a later request uses unblock. Error detection receives FetchError::to_string(), whose public display discards the upstream detail, so many error-triggered fallbacks can never be classified.

Evidence. src/mcp.rs:243-305, 811-847; sanitized error displays in src/errors.rs:12-34.

Fix. Inspect the fast result synchronously and perform one bounded unblock retry in the same tool call under the original debit/idempotency key. Keep structured private error kinds for routing without returning or logging sensitive text.

let fast = fetch_fast().await;
let reason = classify_structured(&fast);
let result = match reason {
    Some(reason) => fetch_unblock_once(reason).await?,
    None => fast?,
};
Medium M-04

Mode routing and proxy parameters contradict the public contract

Impact. /fetch accepts crawl/map/search/extract/screenshot modes but still executes the scrape branch (except unblock), while reporting the requested mode. Fast/auto/extract also send proxy: isp together with deprecated proxy_enabled: false, leaving proxy behavior backend-dependent.

Evidence. README.md:147-161; src/fetch.rs:66-104, 427-433.

Fix. Either restrict /fetch to auto|fast|browser|unblock|raw or dispatch every advertised mode to its matching operation. Stop sending the deprecated proxy boolean.

if route == ProductRoute::Scrape
    && !matches!(mode, Auto | Fast | Browser | Unblock | Raw) {
    return Err(BadRequest("mode is not valid for /fetch".into()));
}

proxy: Self::proxy_type(payload, mode),
proxy_enabled: None,
Medium M-05

Unicode backend errors can panic while being compacted

Impact. Slicing a UTF-8 string at byte 512 panics if that byte is inside a multibyte character. A credit backend response can therefore abort a request while the service is trying to format an error.

Evidence. src/errors.rs:187-193.

Fix. Truncate at a character boundary and add a regression test with a multibyte character crossing the limit.

fn compact_body(body: &str) -> String {
    let body = body.trim();
    if body.len() <= 512 { return body.to_owned(); }
    let end = (0..=512).rev()
        .find(|i| body.is_char_boundary(*i)).unwrap_or(0);
    format!("{}...", &body[..end])
}
Medium M-06

MCP OAuth is introspected twice and its advertised scope/audience contract is inconsistent

Impact. MCP middleware introspects once, discards the context, and the tool introspects again. This doubles latency/load and doubles dependency-failure probability. The metadata advertises resolver:mcp:tools:list, but the MCP gate accepts only fetch scopes; a legacy base audience is also accepted automatically.

Evidence. src/mcp.rs:332-350, 610-621; src/auth.rs:354-375.

Fix. Insert the validated context into request extensions and reuse it in tool dispatch. Apply method-specific discovery/tool scopes, and require explicit configuration before accepting the legacy audience.

// middleware
request.extensions_mut().insert(validated_context);

// tool
let auth_context = parts.extensions.get::<ResolverAuthContext>()
    .ok_or(Unauthorized)?;

// Do not append LEGACY_RESOLVER_AUDIENCE unless explicitly configured.
Medium M-07

The dependency lockfile fails the security audit

Impact. Automated security gates cannot pass. quinn-proto 0.11.14 is covered by a high-severity remote memory-exhaustion advisory and anyhow 1.0.102 by an unsoundness advisory. Current cargo tree does not show either package in the active target graph, which lowers demonstrated runtime exposure but does not justify leaving a red lockfile.

Evidence. Cargo.lock; RUSTSEC-2026-0185 and RUSTSEC-2026-0190 from the 2026-08-17 RustSec database.

Fix. Refresh the lockfile to quinn-proto >=0.11.15 and anyhow >=1.0.103, remove stale inactive packages where possible, and gate every pull request with cargo audit plus a documented exception file for truly unreachable advisories.

cargo update -p quinn-proto --precise 0.11.15
cargo update -p anyhow --precise 1.0.103
cargo audit --deny warnings
Medium M-08

The MCP tool is advertised as read-only despite billing and durable/public side effects

Impact. Clients may make approval and retry decisions based on readOnlyHint=true, but the call debits credits, writes a receipt, and can trigger irreversible provenance publication.

Evidence. src/mcp.rs:148-157, 194-241; provenance publication in C-01.

Fix. Set the hint to false and describe billing/publication in the tool description. If a truly read-only tool is required, separate preview/fetch from charge-and-publish.

annotations(
    title = "Fetch Source",
    read_only_hint = false,
    destructive_hint = false,
    open_world_hint = true
)
Medium M-09

Production lifecycle support is incomplete

Impact. /healthz proves only that the process can answer; it does not check readiness for Spider/auth/credits. There is no graceful shutdown, drain behavior, metrics endpoint, gateway/rate-limit manifest, MCP session-stickiness guidance, or deployment artifact. The README delegates these controls to infrastructure that is absent from the repository.

Evidence. src/main.rs:91-125; README.md:185-193.

Fix. Add separate liveness/readiness endpoints, graceful cancellation, structured metrics, and versioned deployment/gateway configuration. Readiness should validate configuration and dependency reachability without consuming credits.

axum::serve(listener, app)
    .with_graceful_shutdown(shutdown_signal())
    .await?;

Remediation order

  1. Disable implicit/public provenance behavior and add disclosure regression tests before any live traffic.
  2. Replace receipt storage with tenant/project-scoped, durable, random-ID, TTL-bound records.
  3. Correct Spider status handling; ensure failed upstream calls cannot become success receipts/provenance.
  4. Restore MCP host validation and enforce source egress policy, including redirect/DNS checks.
  5. Bound response memory, backend durations, and MCP sessions.
  6. Make the build self-contained and add CI for fmt, Clippy, unit/integration tests, RustSec, and secret scanning.
  7. Unify all routes behind the same auth, credit, receipt, provenance, timeout, and error pipeline.
  8. Finish contract and operations work: idempotency, route/mode semantics, readiness, shutdown, metrics, deployment, and docs.

What is missing

  • Tenant-safe durable receipt repository with TTL/capacity and random IDs.
  • Explicit, private-by-default provenance consent and disclosure policy.
  • SSRF/egress policy and separate authorization for internal destinations.
  • Self-contained dependency strategy and reproducible clean-clone build.
  • CI/CD gates, pinned Rust toolchain, dependency policy, and release metadata.
  • Integration/E2E/concurrency tests with mock auth, credits, Spider, and provenance services.
  • Bounded upstream responses, MCP session eviction, and complete timeout coverage.
  • Product idempotency and documented charge/refund/route-pricing semantics.
  • Readiness, graceful shutdown, metrics, rate-limit/gateway and multi-replica guidance.
  • OpenAPI/JSON Schema, strict unknown-field rejection, complete route/env docs, and MCP config.
  • README backlog: residential proxy rotations, prompt interaction, and Obscura headless research.

Scope note: this repository contains no on-chain Solana program, so signer/PDA/account-ownership and compute-unit checks from the selected review rubric were not applicable. The relevant HTTP, OAuth, MCP, billing, provenance, supply-chain, and production controls were reviewed instead. This is a code and configuration audit, not a formal penetration test of deployed Livy or Spider infrastructure.
